    HA, DR & Security Architecture¶

    Exam Domain: T1 · Architecture — mirroring, async reporting, DR implications, upgrade strategy, and security-driven physical separation

    Overview¶

    Hai khái niệm nền tảng cần nắm rõ trước:

    • HA (High Availability) — đảm bảo hệ thống tiếp tục hoạt động khi một node bị lỗi; đo bằng uptime và failover time. IRIS thực hiện HA qua mirroring với một failover pair (primary + backup).
    • DR (Disaster Recovery) — khả năng phục hồi sau thảm họa (mất cả site, thiên tai, ransomware); đo bằng RTO (Recovery Time Objective — thời gian tối đa có thể chịu downtime) và RPO (Recovery Point Objective — lượng dữ liệu tối đa có thể mất). IRIS thực hiện DR qua async mirror member ở site thứ hai hoặc qua backup/restore.

    Khi kiến trúc bước vào production thật, câu hỏi không chỉ là "data để ở đâu" mà còn là:

    • failover như thế nào? (HA)
    • reporting có ảnh hưởng production không?
    • security/compliance có yêu cầu tách vật lý không?
    • upgrade sẽ tác động ra sao?
    • mất site toàn bộ thì phục hồi thế nào? (DR)

    Subtopic này gom các quyết định kiến trúc xoay quanh HA, DR, security separation, và upgrade planning. Nó được đặt ở module runtime để người học tiếp cận sau khi đã hiểu data model, workload, và deployment basics.

    Nếu cần refresh namespace/database separation trước, xem lại 10 · Architecture Foundations. Nếu cần phân biệt rõ ECP, sharding, và reporting isolation, đọc song song với Production Scaling Patterns.

    Mirroring Basics¶

    Component Role
    Primary node đang phục vụ read/write chính
    Backup / Failover member standby cho HA
    Async member DR hoặc reporting copy có độ trễ nhỏ
    Arbiter tie-breaker để tránh split-brain
    Virtual IP endpoint ổn định cho client connection

    Core Thinking¶

    • mirroring dùng journal shipping / replication logic
    • failover pair phục vụ HA
    • async member phù hợp cho reporting hoặc DR ở site khác

    Gotcha

    Connection string nên trỏ tới Virtual IP hoặc mirror-aware endpoint, không trỏ cứng vào IP vật lý của một node.

    Async Reporting and DR¶

    Async mirror member là pattern rất đáng nhớ cho exam.

    Need Why async member fits
    near-real-time reporting dữ liệu mới với lag nhỏ
    cô lập BI workload không tranh chấp tài nguyên trực tiếp với primary
    DR site xa chấp nhận replication lag

    Trade-off¶

    • có khả năng mất một lượng data bằng replication lag nếu failover vào async member
    • do đó phải khớp với RPO/RTO thực tế của tổ chức

    Which Databases to Mirror¶

    Trong production, thường nên mirror:

    • application data databases
    • application code databases
    • audit database nếu compliance cần giữ audit trail

    Thường không mirror:

    • IRISTEMP
    • IRISLOCALDATA

    Why¶

    Nếu chỉ mirror data mà không mirror code tương ứng, failover có thể tạo code/data mismatch.

    Same Mirror Set vs Fragmented HA¶

    Nếu nhiều database cùng thuộc một ứng dụng HA-critical, thường tốt hơn khi chúng nằm trong cùng mirror set để failover nhất quán.

    Điều này giảm rủi ro:

    • app data đã failover nhưng reference/code database chưa đồng bộ
    • operational behavior khác nhau giữa các database cùng một app boundary

    Security-driven Physical Separation¶

    Một số yêu cầu security/compliance tác động thẳng tới database architecture:

    Requirement Architectural impact
    dữ liệu nhạy cảm cần tách vật lý separate database hoặc separate environment
    retention/audit requirement khác split databases
    encryption/key handling khác nhau plan security boundary từ đầu
    least privilege theo app boundary namespace/database tách rõ hơn

    Điểm chính: security requirement không chỉ là role/permission; nhiều khi nó ép physical separation.

    Encryption and HA¶

    Encryption không ngăn bạn thiết kế HA, nhưng nó ảnh hưởng vận hành:

    • key management phải được tính trên toàn mirror topology
    • restore/failover procedure phải tương thích với encrypted databases
    • security material không nên bị hard-code vào artifact hoặc config versioned

    Upgrade Architecture Implications¶

    Khi upgrade IRIS:

    • databases trong instance không thể vận hành kiểu mixed-version tùy ý
    • multiple databases đòi hỏi downtime/test planning có phối hợp
    • tách code khỏi data giúp test/rollback strategy rõ hơn

    Large-system Upgrade Pattern¶

    Với hệ thống lớn, mirror-based upgrade thường là hướng thực tế:

    1. upgrade backup member
    2. test kỹ
    3. planned failover
    4. upgrade node còn lại

    Điều này giảm downtime hơn in-place upgrade trên production primary.

    Architecture Decision Table¶

    Situation Better direction
    cần HA cho core transactional app mirror failover pair
    cần reporting gần real-time không đụng production async reporting member
    compliance yêu cầu tách dữ liệu nhạy cảm split databases / physical separation
    upgrade hệ lớn cần downtime tối thiểu mirror-assisted upgrade strategy

    Key Points¶

    • ✅ Mirroring là core HA pattern của IRIS
    • ✅ Async mirror member rất hợp cho reporting và DR
    • ✅ Dùng Virtual IP giúp client không phải đổi connection string khi failover
    • ✅ Mirror cả code và data databases để tránh mismatch
    • ✅ Security requirements có thể dẫn tới physical database separation
    • ⚠️ Async member có lag, nên DR plan phải tính RPO thực tế
    • ⚠️ Không mirror IRISTEMP hay IRISLOCALDATA
    • 💡 Nếu đề hỏi vừa HA vừa BI isolation, async reporting member thường là đáp án rất mạnh
